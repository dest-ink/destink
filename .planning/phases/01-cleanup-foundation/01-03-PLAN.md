**Test suites to implement:**

1. **describe('getRetryDelay')**
   - `it('returns 5 minutes for first retry')` — `expect(getRetryDelay(1)).toBe(5 * 60 * 1000)`
   - `it('returns 15 minutes for second retry')` — `expect(getRetryDelay(2)).toBe(15 * 60 * 1000)`
   - `it('returns 45 minutes for third and subsequent retries')` — `expect(getRetryDelay(3)).toBe(45 * 60 * 1000)` and `expect(getRetryDelay(5)).toBe(45 * 60 * 1000)`

2. **describe('runPublishQueue')**
   - `it('publishes a due item and updates status to published')`:
     - mockSelect returns one substack item
     - mockUpdate resolves (called multiple times for status transitions)
     - mockPublishSubstack resolves with `{ ok: true }`
     - Call `await runPublishQueue()`
     - Assert: mockDb.update called (status → publishing, then → published, then draft → published)
     - Assert: mockPublishSubstack called once with draft and channel objects

   - `it('dispatches to LinkedIn publisher for linkedin platform')`:
     - mockSelect returns one item with channel.platform='linkedin'
     - mockPublishLinkedIn resolves
     - Assert: mockPublishLinkedIn called, mockPublishSubstack NOT called

   - `it('retries on publisher failure with incremented retryCount')`:
     - mockSelect returns one item with retryCount=0
     - mockPublishSubstack rejects with Error('API timeout')
     - Assert: mockDb.update called with status='queued', retryCount=1, and a future scheduledFor

   - `it('marks item as permanently failed after max retries')`:
     - mockSelect returns one item with retryCount=2 (so next attempt is retry 3, exceeding max of 3)

     Wait — looking at the code: `retryCount = (item.queue.retryCount ?? 0) + 1` and `if (retryCount > maxRetries)`. maxRetries=3. So if item.queue.retryCount=2, retryCount becomes 3, and 3 > 3 is false — it would retry. If retryCount=3, it becomes 4, and 4 > 3 is true — it fails.

     So: set item.queue.retryCount=3 to trigger permanent failure.
     - mockPublishSubstack rejects
     - Assert: mockDb.update called with status='failed', retryCount=4

   - `it('does nothing when no items are due')`:
     - mockSelect returns empty array
     - Assert: mockDb.update NOT called, no publishers called

   - `it('throws for unknown platform')`:
     - mockSelect returns item with channel.platform='twitter'
     - Assert: mockDb.update eventually called with status containing error about unknown platform

3. **describe('recoverStuckItems')**
   - `it('resets items stuck in publishing older than 15 minutes')`:
     - First mockSelect returns `[{ id: 'stuck-1' }]` (the stuck items query)
     - mockUpdate resolves
     - Call `await recoverStuckItems()`
     - Assert: mockDb.update called with set({ status: 'queued' })
     - Assert: console.warn called (spy on console.warn)

   - `it('does nothing when no stuck items exist')`:
     - mockSelect returns empty array
     - Assert: mockDb.update NOT called

**Important notes for the executor:**
- The `db.update().set().where()` chain is called multiple times per item in runPublishQueue (status→publishing, then status→published or status→queued/failed, then draft→published). The mock must be re-armed or the test must verify call count and arguments via `mockDb.update.mock.calls`.
- Since `mockDb.update` returns the same chain each time, use `mockDb.update.mockReturnValue(chain)` where the chain's `.set()` returns `this` and `.where()` resolves.
- For tests that need multiple select calls (recoverStuckItems uses select, then runPublishQueue also uses select), use `mockDb.select.mockReturnValueOnce()` to differentiate.
- Use `vi.spyOn(console, 'warn').mockImplementation(() => {})` and `vi.spyOn(console, 'log').mockImplementation(() => {})` to suppress and assert log output.
- Use `vi.spyOn(console, 'error').mockImplementation(() => {})` for error log assertions.
