## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Registry initialization pattern
- Extract a shared bootstrap function (e.g. `initRegistries()`) that calls both `initPublisherRegistry()` and `initAdapterRegistry()` — avoids duplicating the init sequence across daemon, job:publish, and job:research
- Each job script calls the shared bootstrap before its business logic, matching the daemon's "init before first use" pattern
- The daemon should also be refactored to use the shared bootstrap for consistency

#### File extension discovery
- `loadDirectory()` should scan for both `.ts` and `.js` suffixes in a single call (or two sequential calls before freezing)
- Both `initPublisherRegistry()` and `initAdapterRegistry()` need to load `.provider.js` / `.adapter.js` in addition to `.ts` variants
- The Registry class currently freezes after one `loadDirectory()` call — this needs adjustment to support scanning for both extensions before freezing

#### Init failure behavior
- Match daemon behavior: crash on init failure (let it throw)
- A CronJob without registries cannot function — failing fast is correct
- Kubernetes CronJob `restartPolicy: OnFailure` handles retries at the orchestration layer

#### Logging
- Log a summary line after init: `[job:publish] Registry initialized: N publisher(s)`
- Per-provider logging stays as-is (console.warn on skip/failure from Registry class)

- Whether to make `loadDirectory()` accept multiple suffixes or call it twice before freezing
- Exact error message formatting

## Summary

The bug is fully understood from direct code inspection — no ambiguity. Both `src/jobs/publish.ts` and `src/jobs/research.ts` use the `publisherRegistry` and `adapterRegistry` singletons (respectively), but neither job script calls the init functions that populate those registries before invoking business logic. The daemon (`src/daemon/index.ts` lines 74–75) correctly calls `await initPublisherRegistry()` then `await initAdapterRegistry()` at startup. The job scripts are missing this step entirely.

The dual-extension discovery gap is a second, independent bug: `initPublisherRegistry()` only scans for `.provider.ts` files and `initAdapterRegistry()` only scans for `.adapter.ts` files. In a production compiled build, provider/adapter files exist as `.provider.js` and `.adapter.js`. The `Registry.loadDirectory()` method freezes (`this.frozen = true`) after each call, but critically, the freeze only blocks the public `register()` method — `loadDirectory()` itself writes directly to `this.providers` and can safely be called twice on the same registry instance without modification to the Registry class.

The fix is three surgical changes: (1) create a shared `initRegistries()` bootstrap function (location is discretionary — Claude chooses), (2) add a second `loadDirectory()` call for the `.js` suffix inside each init function, (3) call the shared bootstrap at the top of each job script's `main()`. The daemon is refactored to use the shared bootstrap for consistency. No new dependencies are required.

**Primary recommendation:** Create `src/lib/bootstrap.ts` exporting `initRegistries()` that wraps both init calls. Update `initPublisherRegistry()` and `initAdapterRegistry()` to scan for both `.ts` and `.js` suffixes via two sequential `loadDirectory()` calls. Wire `src/jobs/publish.ts` and `src/jobs/research.ts` to call `initRegistries()` at the top of `main()`.

### Pattern 1: Shared Bootstrap Function

**What:** A single module that centralizes registry initialization for all entry points (daemon, CronJob scripts, Next.js instrumentation).
**When to use:** Any process that dispatches to `publisherRegistry` or `adapterRegistry`.

```typescript
// src/lib/bootstrap.ts
import { initPublisherRegistry } from '@/lib/publishing/publisher-registry';
import { initAdapterRegistry } from '@/lib/research/adapter-registry';

/**
 * Initialize both provider registries.
 *
 * Call once at startup before any dispatch to publisherRegistry or adapterRegistry.
 * On failure, let it throw — a process without registries cannot function correctly.
 */
export async function initRegistries(): Promise<void> {
  await initPublisherRegistry();
  await initAdapterRegistry();
}
```

### Pattern 2: Dual-Extension loadDirectory Calls

**What:** Each `init*Registry()` function calls `loadDirectory()` twice — once for `.ts` (dev with tsx) and once for `.js` (production compiled output). The Registry class's freeze check is only on `register()`, not on `loadDirectory()`, so two sequential calls are safe.

**Verified by code inspection:** `loadDirectory()` writes via `this.providers.set(key, provider)` at line 91 of `src/lib/providers/registry.ts`, bypassing the frozen check. The second call sets `this.frozen = true` again (idempotent). No modification to Registry class required.

```typescript
// src/lib/publishing/publisher-registry.ts (updated initPublisherRegistry)
export async function initPublisherRegistry(): Promise<void> {
  const providersDir = path.resolve(process.cwd(), 'src/lib/publishing/providers');
  const validate = (mod: unknown) => (isPublisherProvider(mod) ? mod : null);

  // Development: tsx runs .ts source files directly
  await publisherRegistry.loadDirectory(providersDir, '.provider.ts', validate);
  // Production: compiled .js output
  await publisherRegistry.loadDirectory(providersDir, '.provider.js', validate);
}
```

```typescript
// src/lib/research/adapter-registry.ts (updated initAdapterRegistry)
export async function initAdapterRegistry(): Promise<void> {
  const adaptersDir = path.resolve(process.cwd(), 'src/lib/research/adapters');
  const validate = (mod: unknown): ResearchAdapter | null =>
    isResearchAdapter(mod) ? mod : null;

  await adapterRegistry.loadDirectory(adaptersDir, '.adapter.ts', validate);
  await adapterRegistry.loadDirectory(adaptersDir, '.adapter.js', validate);
}
```

### Pattern 3: Job Script Bootstrap Wiring

**What:** Each job's `main()` calls `initRegistries()` before business logic. Follows the crash-on-failure pattern the daemon already uses.

```typescript
// src/jobs/publish.ts (updated)
import { pool } from '@/db/client';
import { runPublishQueue } from '@/lib/publishing/queue-runner';
import { initRegistries } from '@/lib/bootstrap';
import { publisherRegistry } from '@/lib/publishing/publisher-registry';

async function main(): Promise<void> {
  const start = new Date().toISOString();
  console.log(`[job:publish] Starting at ${start}`);

  // Init failure throws — CronJob cannot function without registries.
  await initRegistries();
  console.log(`[job:publish] Registry initialized: ${publisherRegistry.keys().length} publisher(s)`);

  try {
    await runPublishQueue();
    const finish = new Date().toISOString();
    console.log(`[job:publish] Finished at ${finish}`);
  } finally {
    await pool.end();
  }
}

main().catch((err: unknown) => {
  console.error('[job:publish] Unhandled error:', err);
  process.exit(1);
});
```

### Pattern 4: Daemon Refactor to Use Shared Bootstrap

**What:** Replace inline dual `await init*()` calls in `src/daemon/index.ts` with the shared `initRegistries()`. Maintains identical runtime behavior.

```typescript
// src/daemon/index.ts (updated lines 74-75)
import { initRegistries } from '@/lib/bootstrap';

// Initialize provider registries before first tick.
// If initialization fails, let it crash — a daemon without registries cannot function.
await initRegistries();
```

### Anti-Patterns to Avoid
- **Calling `runPublishQueue()` before `initPublisherRegistry()`:** The `publisherRegistry` singleton is empty. `publisherRegistry.get(platform)` returns `undefined`, throwing `"No publisher registered for platform 'X'"` for every queued item — silent data loss in terms of publish outcomes.
- **Calling `runResearch()`/`runResearchForChannel()` before `initAdapterRegistry()`:** `adapterRegistry.getAll()` returns `[]`, `runResearch()` fan-outs to zero adapters, returns empty sources, Claude generates topics from nothing — silent failure with no error.
- **Swallowing init errors in job scripts:** Do NOT wrap `initRegistries()` in try/catch. Let it throw and propagate to the top-level `.catch()` that calls `process.exit(1)`. Kubernetes `restartPolicy: OnFailure` handles retries.
- **Calling `register()` after `loadDirectory()`:** This throws "Registry is frozen". Providers must be registered before or inside the discovery scan. Not a concern here since we only use `loadDirectory()`.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|

## Common Pitfalls

### Pitfall 1: Assuming Registry.loadDirectory() freeze blocks second call

**What goes wrong:** Developer reads "registry is frozen after loadDirectory()" and concludes a second `loadDirectory()` call will fail.
**Why it happens:** The freeze check lives inside `register()` (line 37 of `registry.ts`), not inside `loadDirectory()`. The `loadDirectory()` method writes to `this.providers` directly.
**How to avoid:** Verify by reading `loadDirectory()` source (lines 63–99): it never checks `this.frozen`. Two sequential calls are safe with current code.
**Warning signs:** If a test for the second loadDirectory call throws "Registry is frozen" — that would indicate the code was changed to add a freeze check to loadDirectory itself, requiring a different approach.

### Pitfall 2: Duplicate provider registration in dual-extension scan

**What goes wrong:** In development (tsx), `.provider.ts` files exist. The second `loadDirectory()` call for `.provider.js` finds no matching files (tsx doesn't compile to `.js` in `src/`). In production, the first call (`.provider.ts`) finds no files (source `.ts` files not in compiled output dir), only the second succeeds. So the two calls do NOT produce duplicates — only one extension exists in each environment.
**Why it happens:** Good: this is the desired behavior. But if the compiled output lands in the same `src/lib/publishing/providers/` directory as source (e.g. in some monorepo setups), duplicates could theoretically arise.
**How to avoid:** Confirm that the production build output directory differs from source (standard for Next.js: `.next/` standalone). The `process.cwd() + 'src/lib/publishing/providers'` path resolves to source only — not a problem.
**Warning signs:** Registry contains the same provider registered twice under the same key (Map.set is idempotent by key, so it would just overwrite — no crash, but a warning might appear if platform key collision is logged).

### Pitfall 3: Next.js instrumentation double-init

**What goes wrong:** `src/instrumentation.ts` already calls `initPublisherRegistry()` and `initAdapterRegistry()` when the Next.js server starts. If that path is changed to call `initRegistries()` instead, it still works — but if the shared bootstrap is called separately from a test or route before instrumentation fires, the second call could fail due to the Registry singleton being frozen.
**Why it happens:** `publisherRegistry` and `adapterRegistry` are module-level singletons. Multiple calls to their init functions will call `loadDirectory()` again on an already-frozen registry — but since `loadDirectory()` doesn't check `frozen`, this silently re-scans. Keys already present will be overwritten with the same values (idempotent). Not a crash, but slightly wasteful.
**How to avoid:** This phase scope is only job scripts and daemon — `instrumentation.ts` is not being changed. Keep it as-is. The instrumentation path is entirely separate (Next.js server process) from job script processes.
**Warning signs:** Multiple "Registry initialized: N publisher(s)" log lines for the same process.

### Pitfall 4: Import path — `@/lib/bootstrap` vs relative

**What goes wrong:** The `@/` alias is configured in `tsconfig.json` and `vitest.config.ts` (via `vite-tsconfig-paths`). Job scripts (`src/jobs/*.ts`) run via tsx which also resolves `@/` aliases. Using a relative path (`../lib/bootstrap`) works but diverges from the project convention.
**Why it happens:** tsx resolves `@/` as the tsconfig path alias.
**How to avoid:** Use `@/lib/bootstrap` import consistently. Check `tsconfig.json` to confirm the alias is defined.
**Warning signs:** "Cannot find module '@/lib/bootstrap'" at runtime — check tsx version and tsconfig paths.
