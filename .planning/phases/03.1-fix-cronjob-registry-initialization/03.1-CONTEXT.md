# Phase 3.1: Fix CronJob Registry Initialization - Context

**Gathered:** 2026-02-28
**Status:** Ready for planning

<domain>
## Phase Boundary

Standalone CronJob scripts (`job:publish`, `job:research`) must initialize provider/adapter registries before dispatching work, and registry auto-discovery must work with both `.ts` (dev) and compiled `.js` (production) files. This closes INT-01, INT-02, and the broken `job:publish` flow identified in the v1.0 audit.

</domain>

<decisions>
## Implementation Decisions

### Registry initialization pattern
- Extract a shared bootstrap function (e.g. `initRegistries()`) that calls both `initPublisherRegistry()` and `initAdapterRegistry()` — avoids duplicating the init sequence across daemon, job:publish, and job:research
- Each job script calls the shared bootstrap before its business logic, matching the daemon's "init before first use" pattern
- The daemon should also be refactored to use the shared bootstrap for consistency

### File extension discovery
- `loadDirectory()` should scan for both `.ts` and `.js` suffixes in a single call (or two sequential calls before freezing)
- Both `initPublisherRegistry()` and `initAdapterRegistry()` need to load `.provider.js` / `.adapter.js` in addition to `.ts` variants
- The Registry class currently freezes after one `loadDirectory()` call — this needs adjustment to support scanning for both extensions before freezing

### Init failure behavior
- Match daemon behavior: crash on init failure (let it throw)
- A CronJob without registries cannot function — failing fast is correct
- Kubernetes CronJob `restartPolicy: OnFailure` handles retries at the orchestration layer

### Logging
- Log a summary line after init: `[job:publish] Registry initialized: N publisher(s)`
- Per-provider logging stays as-is (console.warn on skip/failure from Registry class)

### Claude's Discretion
- Shared bootstrap location (new file vs. re-export from existing module)
- Whether to make `loadDirectory()` accept multiple suffixes or call it twice before freezing
- Exact error message formatting

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `Registry<T>` class (`src/lib/providers/registry.ts`): Generic registry with `loadDirectory()`, `register()`, `get()`, `getAll()`. Currently freezes after first `loadDirectory()` call — needs modification to support dual-extension scanning
- `initPublisherRegistry()` (`src/lib/publishing/publisher-registry.ts`): Scans `src/lib/publishing/providers/` for `*.provider.ts` files. Missing `.js` scan
- `initAdapterRegistry()` (`src/lib/research/adapter-registry.ts`): Scans `src/lib/research/adapters/` for `*.adapter.ts` files. Missing `.js` scan
- `isPublisherProvider()` and `isResearchAdapter()` type guards: Validate module exports against provider contracts

### Established Patterns
- **Daemon init pattern** (`src/daemon/index.ts:74-75`): Calls `initPublisherRegistry()` then `initAdapterRegistry()` at top-level before scheduling cron
- **Next.js instrumentation** (`src/instrumentation.ts`): Uses dynamic imports inside `register()` hook to init both registries at server start
- **Job script pattern** (`src/jobs/*.ts`): Wrap business logic in `main()` with try/finally for `pool.end()`, catch at top level for crash-exit

### Integration Points
- `src/jobs/publish.ts`: Needs registry init before `runPublishQueue()` call
- `src/jobs/research.ts`: Needs registry init before `runResearchForChannel()` call
- `src/lib/publishing/queue-runner.ts`: Uses `publisherRegistry.get(platform)` — fails silently if registry empty
- `src/lib/research/orchestrator.ts`: Uses `adapterRegistry.getAll()` — returns empty array if registry empty

</code_context>
